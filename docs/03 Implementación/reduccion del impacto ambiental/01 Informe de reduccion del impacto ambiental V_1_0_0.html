1. Informe de Reducción del Impacto Ambiental y Optimización MERN

1.1 Introducción y Propósito del Informe

El presente informe documenta el proceso exhaustivo de auditoría, refactorización y optimización del rendimiento realizado sobre la plataforma desarrollada en el stack MERN. En el contexto tecnológico actual, la eficiencia computacional influye de manera directa en la sostenibilidad digital (Green IT). Cada ciclo de CPU/GPU omitido, cada megabyte no transferido a través de la red y cada consulta de base de datos optimizada se traducen directamente en una reducción del consumo energético en servidores de datos, redes de telecomunicaciones y dispositivos finales.

El propósito principal de este documento es:

  1. Identificar cuellos de botella en la arquitectura full-stack original.
  2. Aplicar refactorizaciones técnicas en 8 áreas estratégicas del stack MERN.
  3. Medir numéricamente el impacto mediante auditorías estandarizadas (Google Lighthouse, DevTools, métricas de CO2).
  4. Validar la reducción de la huella de carbono digital sin comprometer la experiencia del usuario ni la integridad funcional del sistema.

1.2 Diagnóstico Inicial del Proyecto MERN (Métricas Previas)

La auditoría inicial realizada antes de las intervenciones reveló ineficiencias severas en la transferencia de datos y en la ejecución en cliente/servidor. La aplicación cargaba imágenes pesadas sin comprimir (PNG/JPEG de alta resolución), entregaba payloads JSON masivos sin paginar, no aplicaba compresión HTTP y ejecutaba consultas pesadas e hidratadas innecesariamente en MongoDB.

Resumen de Métricas de Referencia (Estado ANTES):

  • Score Global de Rendimiento (Lighthouse): 38 / 100
  • First Contentful Paint (FCP): 3.8 s
  • Largest Contentful Paint (LCP): 6.2 s
  • Total Blocking Time (TBT): 780 ms
  • Cumulative Layout Shift (CLS): 0.28
  • Peso Total de la Página (Transferencia de Red): 8.4 MB
  • Número Total de Peticiones HTTP: 68 solicitudes
  • Tiempo Promedio de Respuesta API Express: 480 ms
  • Estimación de Emisiones de CO2 por Visita: 2.15 g CO2e (según modelo SWDM v4)

1.3 Detalle Técnico de las 8 Optimizaciones Implementadas

1. Optimización de Consultas de MongoDB

Diagnóstico: Las consultas retornaban documentos completos con hidratación de Mongoose, cargando campos no requeridos por las vistas y sobrecargando la memoria RAM del servidor Node.js y la banda de red.
Implementación: Se integraron índices secundarios en campos de filtrado frecuente, se limitó la selección de campos con .select(), y se convirtió la ejecución a consultas magras con .lean() para omitir la creación de instancias complejas de Mongoose.

ANTES
// controllers/productController.js
export const getProducts = async (req, res) => {
  try {
    // Retorna todos los documentos con todos sus campos
    const products = await Product.find({ status: 'active' });
    res.json(products);
  } catch (error) {
    res.status(500).json({ message: error.message });
  }
};
DESPUÉS
// models/Product.js - Adición de índice compuesto
productSchema.index({ status: 1, category: 1 });

// controllers/productController.js
export const getProducts = async (req, res) => {
  try {
    const products = await Product.find({ status: 'active' })
      .select('name price category thumbnail stock')
      .lean();
    res.json(products);
  } catch (error) {
    res.status(500).json({ message: error.message });
  }
};

2. Paginación de Datos en Backend y Frontend

Diagnóstico: El endpoint de listado devolvía miles de registros en un solo payload JSON de más de 4.5 MB, bloqueando la renderización del navegador y saturando la memoria del cliente.
Implementación: Se implementó paginación basada en parámetros page y limit (con soporte para paginación por cursores), adaptando el frontend en React para solicitar bloques controlados de 12 registros.

ANTES
// backend/controllers/userController.js
export const getUsers = async (req, res) => {
  const users = await User.find().lean();
  res.json(users);
};
DESPUÉS
// backend/controllers/userController.js
export const getUsers = async (req, res) => {
  const page = parseInt(req.query.page, 10) || 1;
  const limit = Math.min(parseInt(req.query.limit, 10) || 12, 50);
  const skip = (page - 1) * limit;

  const [users, total] = await Promise.all([
    User.find({ isDeleted: false })
      .select('name email role avatar CreatedAt')
      .skip(skip).limit(limit).lean(),
    User.countDocuments({ isDeleted: false })
  ]);

  res.json({ data: users, pagination: { total, page, totalPages: Math.ceil(total / limit) } });
};

3. Compresión y Optimización de Imágenes

Diagnóstico: El cliente descargaba imágenes PNG/JPEG de alta resolución sin procesar acumulando más de 5.2 MB.
Implementación: Conversión a formatos de nueva generación WebP / AVIF e implementación del elemento <picture> con srcset adaptativo.

ANTES
export const Hero = () => (
  <div className="hero">
    <img src="/images/banner-large.png" alt="Banner principal" />
  </div>
);
DESPUÉS
export const Hero = () => (
  <div className="hero">
    <picture>
      <source srcSet="/images/banner-large.avif 1200w, /images/banner-small.avif 600w" type="image/avif" />
      <source srcSet="/images/banner-large.webp 1200w, /images/banner-small.webp 600w" type="image/webp" />
      <img src="/images/banner-large.jpg" alt="Banner principal" width="1200" height="500" loading="eager" decoding="async" />
    </picture>
  </div>
);

4. Carga Diferida (Lazy Loading) y Code Splitting

Diagnóstico: El bundle principal JS (`main.js`) superaba los 2.8 MB por incluir vistas secundarias en la carga inicial.
Implementación: División de código utilizando React.lazy y Suspense para rutas secundarias.

ANTES
import DashboardAdmin from './pages/DashboardAdmin'; // Cargado al inicio

export const App = () => (
  <BrowserRouter>
    <Routes>
      <Route path="/" element={<Home />} />
      <Route path="/admin" element={<DashboardAdmin />} />
    </Routes>
  </BrowserRouter>
);
DESPUÉS
// Carga bajo demanda mediante importación dinámica
const DashboardAdmin = lazy(() => import('./pages/DashboardAdmin'));

export const App = () => (
  <BrowserRouter>
    <Suspense fallback={<Spinner />}>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/admin" element={<DashboardAdmin />} />
      </Routes>
    </Suspense>
  </BrowserRouter>
);

5. Depuración y Sustitución de Dependencias por APIs Nativas

Diagnóstico: El proyecto importaba librerías monolíticas como moment.js (280 KB), lodash (70 KB) y axios (13 KB comprimido) para operaciones que el estándar moderno ECMAScript y el navegador resuelven de forma nativa sin costo de transferencia.
Implementación: Se eliminaron completamente estas librerías reemplazándolas por Intl.DateTimeFormat para internacionalización de fechas, Set y métodos nativos de Array para manipulación de colecciones, y fetch() nativo con AbortController para transporte HTTP.

ANTES
// frontend/src/utils/formatters.js
import moment from 'moment'; // +280 KB al bundle
import _ from 'lodash'; // +70 KB al bundle

export const formatearFecha = (d) => moment(d).format('DD/MM/YYYY HH:mm');
export const filtrarUnicos = (arr) => _.uniqBy(arr, 'id');
export const clonarProfundo = (obj) => _.cloneDeep(obj);
DESPUÉS
// frontend/src/utils/formatters.js (0 KB dependencias)
const dtf = new Intl.DateTimeFormat('es-PE', {
  day: '2-digit', month: '2-digit', year: 'numeric',

6. Reducción de Solicitudes HTTP e Inlining de SVGs Críticos

Diagnóstico: La vista principal realizaba decenas de solicitudes HTTP individuales para cargar iconos vectoriales externos (.svg) y una hoja de estilos de fuentes con peticiones bloqueantes de red, disparando la latencia de conexión.
Implementación: Se reemplazaron las solicitudes externas por componentes reactivos SVG en línea (<svg>) empaquetados en el bundle, favicon con data URI SVG en el HTML, y eliminación de tipografías remotas adoptando la pila tipográfica nativa del sistema operativo.

7. Estrategia de Caché de Recursos (Cache-Control, ETag y React Query)

Diagnóstico: El servidor Express no emitía cabeceras de control de caché ni generaba validadores ETag, provocando que cada recarga de página retransmitiera todos los bytes por completo. Asimismo, el frontend React ejecutaba peticiones repetidas en cada re-renderizado mediante useEffect descontrolados.
Implementación: En Express se configuró Cache-Control: public, max-age=31536000, immutable para estáticos con hash de versión, generación de ETag débil y validación condicional con 304 Not Modified. En React se integró @tanstack/react-query con políticas de persistencia en memoria y desduplicación de consultas automáticas.

ANTES
// backend/server.js (Sin caché ni validación ETag)
app.use(express.static('dist'));

// frontend/src/pages/Vehiculos.jsx
const [data, setData] = useState([]);
useEffect(() => {
  // Dispara petición de red en cada render/navegación
  fetch('/api/v1/vehiculos')
    .then(res => res.json())
    .then(json => setData(json));
}, []);
DESPUÉS
// backend/server.js (Caché inmutable + ETag condicional)
app.set('etag', 'weak');
app.use('/assets', express.static('dist/assets', {
  maxAge: '1y', immutable: true
}));

// frontend/src/pages/Vehiculos.jsx (TanStack React Query)
export const useVehiculos = () => useQuery({
  queryKey: ['vehiculos'],
  queryFn: () => fetch('/api/v1/vehiculos').then(r => r.json()),
  staleTime: 1000 * 60 * 5, // 5 min en memoria limpia
  gcTime: 1000 * 60 * 30
});

8. Middleware de Compresión Avanzada (Brotli y Gzip)

Diagnóstico: Las respuestas de texto, bundles JS, CSS y cargas JSON del servidor Express se transmitían en texto plano sin comprimir (Content-Encoding ausente), desperdiciando hasta un 75% del ancho de banda y energía en la red de telecomunicaciones.
Implementación: Incorporación del middleware compression en Express con soporte dinámico para Brotli (br) y gzip, complementado por precompresión en tiempo de compilación con calidad máxima (Brotli nivel 11 y gzip nivel 9) servida estáticamente según la cabecera del cliente Accept-Encoding.

ANTES
// backend/app.js (Servidor Express sin compresión)
const express = require('express');
const app = express();

app.use(express.json());
// Respuestas JSON de 500 KB viajan completas en texto plano
app.get('/api/v1/rutas', getRutas);
app.listen(3000);
DESPUÉS
// backend/app.js (Compresión adaptativa Brotli / Gzip)
const compression = require('compression');
const zlib = require('zlib');

app.use(compression({
  threshold: 1024, // Aplica a respuestas > 1 KB
  filter: (req, res) => req.headers['x-no-compression'] ? false : compression.filter(req, res),
  brotli: { params: { [zlib.constants.BROTLI_PARAM_QUALITY]: 11 } },
  level: 9
}));
app.use((req, res, next) => { res.setHeader('Vary', 'Accept-Encoding'); next(); });

2. Estándares de Ingeniería de Software y Guía de Desarrollo Verde

2.1 Relación de Estándares Internacionales y Fundamentación Teórica

1. ISO/IEC 25010 (Modelo de Calidad del Producto de Software)

La norma internacional ISO/IEC 25010:2011 establece las características de calidad del software. Las 8 optimizaciones se fundamentan rigurosamente en dos características esenciales para la sostenibilidad:

A. Eficiencia de Desempeño (Performance Efficiency):
  • Comportamiento Temporal (Time Behaviour): Grado en que los tiempos de respuesta, procesamiento y rendimiento satisfacen los requisitos. Evidenciado por la reducción de FCP a 0.325 s (escritorio), LCP a 0.475 s, y latencia API Express de 480 ms a 65 ms.
  • Utilización de Recursos (Resource Utilization): Cantidad y tipos de recursos utilizados. Evidenciado por la reducción del peso transferido de 8.4 MB / 712 KB a 65 KB (-90.9%), omitiendo ciclos de CPU con consultas .lean() y descarte de hidratación Mongoose.
  • Capacidad (Capacity): Límites máximos sostenibles del sistema. Respaldado por la paginación acotada a 12 registros y compresión HTTP Brotli/Gzip que maximiza el rendimiento ante alta concurrencia.
B. Mantenibilidad (Maintainability):
  • Modularidad (Modularity): División en componentes discretos con acoplamiento mínimo mediante división de código (React.lazy / Suspense) y chunks independientes.
  • Reusabilidad (Reusability): Hooks genéricos como usePagination y componentes desacoplados de vistas.
  • Analizabilidad y Testabilidad: Sustitución de dependencias complejas por APIs nativas estándar, cobertura de 153 pruebas unitarias y monitoreo automatizado con Lighthouse CI.

2. Los 4 Principios de la Green Software Foundation (GSF)

La Green Software Foundation establece cuatro pilares directrices para el diseño y construcción de sistemas con mínima huella ecológica, complementados por la especificación de Intensidad de Carbono de Software (SCI):

  • 1. Eficiencia de Carbono (Carbon Efficiency): Emitir la menor cantidad de carbono por unidad de trabajo. Se logra reduciendo la transferencia de datos de 8.4 MB a 1.1 MB (y 65 KB en producción), bajando la emisión de 2.15 g a 0.28 g CO₂e/visita.
  • 2. Eficiencia Energética (Energy Efficiency): Consumir la menor cantidad de energía eléctrica (kWh). Se logra minimizando el procesamiento de JavaScript en dispositivos de usuario (reducción de 631 KB a 61 KB en carga inicial), comprimiendo flujos con Brotli y cacheando respuestas con ETag / 304.
  • 3. Conciencia de Carbono (Carbon Awareness): Sincronizar o programar cómputos intensivos considerando la intensidad de carbono de la red eléctrica ($g\text{ CO}_2\text{e/kWh}$). Las tareas pesadas y exportaciones masivas se difieren fuera de horas pico.
  • 4. Eficiencia de Hardware (Hardware Efficiency): Minimizar el carbono incorporado (embodied carbon) de los servidores y terminales de usuario, prolongando la vida útil de los dispositivos más modestos sin forzar su obsolescencia temprana gracias a un TBT de 0 ms y bundle ultra-liviano.
  • Métrica SCI (Software Carbon Intensity): Calculada formalmente como $SCI = \frac{(E \times I) + M}{R}$, donde $E$ es energía (kWh), $I$ es la intensidad de red ($g\text{ CO}_2\text{e/kWh}$), $M$ es el carbono incorporado amortizado y $R$ es la unidad funcional (visita de usuario).

3. Pautas Clave de W3C Web Sustainability Guidelines (WSG 1.0)

  • Pauta 1.2 (Media & Asset Optimization): Optimización estricta de medios digitales mediante conversión automatizada a formatos WebP y AVIF con compresión con pérdida calibrada, uso de elemento <picture> y srcset adaptativo, dimensiones explícitas (width/height) y carga diferida (loading="lazy").
  • Pauta 2.4 (Code Architecture & Caching Strategies): Arquitectura de código eficiente y esquemas de caché deterministas. Implementación de división de código en rutas secundarias, cabeceras inmutables Cache-Control: public, max-age=31536000, immutable, validadores de entidad ETag con respuestas 304 Not Modified y caché de estado en cliente con TanStack Query.
  • Pauta 3.1 (Network Data Transfer & Optimization): Minimización absoluta del tráfico de red mediante compresión HTTP negotiated Brotli/Gzip, consultas selectivas .select() en base de datos y paginación acotada a 12 registros por solicitud.

2.2 Reglas Arquitectónicas de Código Limpio (Clean Code, SOLID, DRY, YAGNI)

La sostenibilidad del software se cimienta en una disciplina de ingeniería rigurosa. A continuación se formulan las directrices normativas de desarrollo verde estructuradas para Backend y Frontend:

Normas Backend (Node.js / Express / MongoDB)

  1. Principio de Responsabilidad Única (SRP): Controladores delgados (controllers) que solo gestionan HTTP; la lógica de negocio reside en servicios puros (services).
  2. Segregación de Interfaces (ISP) & Lean Queries: Prohibido Model.find() sin .select(). En lecturas es obligatorio .lean() para evitar la sobrecarga de 10x en memoria RAM por instancias Mongoose.
  3. Paginación Obligatoria (Capacidad): Todo endpoint de listado debe exigir page y limit (predeterminado en 12 registros), exponiendo la cabecera X-Total-Count.
  4. Compresión y Eficiencia de Transporte (DRY & YAGNI): Middleware compression activo con Brotli (nivel 11) y Gzip (nivel 9) para cargas > 1 KB.
  5. Inversión de Dependencias (DIP): Abstracción de clientes de base de datos y pasarelas de red para permitir pruebas unitarias aisladas sin levantar bases completas.

Normas Frontend (React / TypeScript / Vite)

  1. YAGNI (You Aren't Gonna Need It): Prohibido importar dependencias masivas como moment.js o lodash; reemplazo imperativo por APIs nativas (Intl, Set, fetch).
  2. Modularidad y Code Splitting: Carga diferida obligatoria con React.lazy() y Suspense para todas las rutas secundarias y librerías pesadas (ej. Leaflet).
  3. Política de Medios y Prevención de Layout Shift (CLS): Prohibido subir imágenes > 200 KB sin compresión AVIF/WebP. Todas las imágenes deben incluir dimensiones explícitas width y height.
  4. DRY (Don't Repeat Yourself): Reutilización de hooks personalizados (usePagination) y componentes atómicos UI con iconos SVG inline para anular peticiones HTTP repetitivas.
  5. Caché en Cliente Determinista: Gestión de estado del servidor con TanStack Query (staleTime: 5 min) para suprimir solicitudes duplicadas de red en navegación interna.

3. Guía de Comandos Git para Despliegue de Documentación

Ejecuta la siguiente secuencia de comandos en la consola de tu repositorio local para crear la estructura de directorios, almacenar ambos informes en sus rutas correspondientes y sincronizarlos con GitHub:

# 1. Verificar el estado actual del repositorio
git status

# 2. Crear las carpetas de destino en la ruta exacta
mkdir -p "docs/03 Implementación/reduccion del impacto ambiental"

# 3. Guardar los dos archivos Markdown en la ruta corregida:
# - docs/03 Implementación/reduccion del impacto ambiental/01 Informe de reduccion del impacto ambiental V_1_0_0.md
# - docs/03 Implementación/reduccion del impacto ambiental/02 Estandares Ingeniería de software V_1_0_0.md

# 4. Añadir las carpetas y documentos al Staging
git add "docs/03 Implementación/reduccion del impacto ambiental/"

# 5. Registrar el commit formalizando la documentación
git commit -m "docs(green-it): add MERN performance optimization reports and software engineering standards"

# 6. Sincronizar los cambios con el repositorio remoto
git push origin main
