## 2. Objetivo

Definir los requisitos no funcionales del sistema **EcoLogística Lima** mediante atributos de calidad verificables y medibles, utilizando escenarios de calidad compatibles con la estructura propuesta por **arc42** y tomando como referencia las categorías de calidad de **ISO/IEC 25010**.

Los requisitos se expresan con métricas cuantificables para evitar términos ambiguos y permitir su validación mediante pruebas, mediciones o revisiones documentales.

---

## 3. Criterios de especificación

Cada requisito no funcional se formula considerando los siguientes elementos:

- **Fuente:** actor, sistema o evento que origina el estímulo.
- **Estímulo:** condición o evento que activa el comportamiento esperado.
- **Entorno:** condiciones operativas bajo las cuales ocurre el estímulo.
- **Artefacto:** parte del sistema afectada.
- **Respuesta:** comportamiento esperado del sistema.
- **Medida de respuesta:** métrica verificable que determina el cumplimiento.

Además, cada RNF debe cumplir los criterios SMART:

- **Específico:** expresa claramente el atributo de calidad evaluado.
- **Medible:** contiene una métrica o umbral verificable.
- **Alcanzable:** puede implementarse y comprobarse en el contexto del proyecto.
- **Relevante:** contribuye directamente a la operación de EcoLogística Lima.
- **Limitado en el tiempo:** puede verificarse durante una fase, prueba o condición temporal definida.

# 4. Requisitos No Funcionales

## RNF-001: Rendimiento del algoritmo de optimización

**Categoría ISO/IEC 25010:** Eficiencia de desempeño  
**Prioridad:** Alta

### Declaración del requisito

El sistema debe generar una solución válida de optimización de rutas en un tiempo máximo de **45 segundos** cuando procese hasta **150 pedidos y 15 vehículos** bajo condiciones normales de operación.

Ante eventos que requieran re-optimización dinámica, el sistema debe generar una nueva solución válida en un tiempo menor o igual a **30 segundos**.

### Escenario de Calidad

| Elemento del escenario | Descripción del comportamiento |
|---|---|
| **Fuente** | Operador logístico o evento de actualización de ruta |
| **Estímulo** | Solicitud de cálculo o recálculo de rutas |
| **Entorno** | Operación normal, incluyendo horas de alta variación del tráfico |
| **Artefacto** | Módulo de optimización de rutas |
| **Respuesta** | Generar una solución válida considerando pedidos, vehículos y restricciones operativas |
| **Medida de respuesta** | ≤ 45 s para hasta 150 pedidos y 15 vehículos; ≤ 30 s para re-optimización dinámica |

### Método de verificación

- Ejecutar pruebas de rendimiento con conjuntos de datos de hasta 150 pedidos y 15 vehículos.
- Registrar el tiempo total desde el envío de la solicitud hasta la obtención de una solución válida.
- Repetir las pruebas en escenarios de cálculo inicial y re-optimización.

### Evaluación SMART

| Criterio | Cumplimiento | Justificación |
|---|---|---|
| Específico | Sí | Define claramente el comportamiento esperado del módulo de optimización. |
| Medible | Sí | Establece límites de 45 s y 30 s. |
| Alcanzable | Sí | Puede validarse mediante pruebas controladas de rendimiento. |
| Relevante | Sí | La rapidez de cálculo es crítica para la planificación de reparto. |
| Limitado en el tiempo | Sí | El cumplimiento se valida durante cada ejecución del algoritmo. |

## RNF-002: Seguridad de la aplicación y protección de datos

**Categoría ISO/IEC 25010:** Seguridad  
**Prioridad:** Alta

### Declaración del requisito

El sistema debe proteger los datos de clientes, conductores y usuarios mediante controles que prevengan vulnerabilidades críticas asociadas a **OWASP Top 10**, incluyendo intentos de inyección SQL, XSS, CSRF y fallas de autenticación o autorización.

El tratamiento de información personal deberá contemplar los requerimientos aplicables de la **Ley N.° 29733, Ley de Protección de Datos Personales del Perú**.

### Escenario de Calidad

| Elemento del escenario | Descripción del comportamiento |
|---|---|
| **Fuente** | Usuario no autorizado o atacante externo |
| **Estímulo** | Intento de acceso indebido, manipulación de entradas o ejecución de una vulnerabilidad web |
| **Entorno** | Aplicación desplegada y disponible para usuarios autorizados |
| **Artefacto** | Módulos de autenticación, autorización, API y persistencia de datos |
| **Respuesta** | Rechazar la operación no autorizada, conservar la integridad de los datos y registrar el evento cuando corresponda |
| **Medida de respuesta** | 0 vulnerabilidades críticas explotables identificadas en la revisión de seguridad de los controles evaluados |

### Método de verificación

- Ejecutar pruebas de seguridad sobre entradas, autenticación y autorización.
- Revisar los controles frente a las categorías aplicables de OWASP Top 10.
- Verificar que usuarios sin permisos no puedan acceder a información o acciones restringidas.
- Revisar el tratamiento de datos personales considerados por el sistema.

### Evaluación SMART

| Criterio | Cumplimiento | Justificación |
|---|---|---|
| Específico | Sí | Define los riesgos principales que deben prevenirse. |
| Medible | Sí | Se exige 0 vulnerabilidades críticas explotables en la evaluación definida. |
| Alcanzable | Sí | Puede verificarse mediante pruebas de seguridad y control de acceso. |
| Relevante | Sí | El sistema gestiona información de clientes y conductores. |
| Limitado en el tiempo | Sí | Se valida antes de cada liberación evaluada del sistema. |

## RNF-003: Accesibilidad de la interfaz

**Categoría ISO/IEC 25010:** Capacidad de interacción / Usabilidad  
**Prioridad:** Alta

### Declaración del requisito

La interfaz de usuario debe cumplir con las directrices **WCAG 2.1 nivel AA** en las pantallas principales utilizadas por conductores, operadores y clientes.

La interfaz deberá presentar elementos visuales comprensibles, iconografía reconocible y contraste suficiente para facilitar su uso por personas con distintos niveles de familiaridad tecnológica.

### Escenario de Calidad

| Elemento del escenario | Descripción del comportamiento |
|---|---|
| **Fuente** | Usuario del sistema |
| **Estímulo** | Navegación o interacción con una pantalla funcional |
| **Entorno** | Uso normal desde un dispositivo compatible |
| **Artefacto** | Interfaz web y vistas orientadas a conductores y operadores |
| **Respuesta** | Presentar información y controles de forma perceptible, operable y comprensible |
| **Medida de respuesta** | Cumplimiento de los criterios aplicables de WCAG 2.1 nivel AA en las pantallas evaluadas |

### Método de verificación

- Realizar revisión de accesibilidad de las pantallas principales.
- Verificar contraste, navegación, etiquetas y comprensión de controles.
- Registrar incumplimientos y repetir la revisión después de las correcciones.

### Evaluación SMART

| Criterio | Cumplimiento | Justificación |
|---|---|---|
| Específico | Sí | Se identifica claramente el estándar de accesibilidad. |
| Medible | Sí | El resultado se verifica frente a WCAG 2.1 AA. |
| Alcanzable | Sí | Puede revisarse durante el desarrollo de la interfaz. |
| Relevante | Sí | El sistema debe ser utilizable por conductores y usuarios con distintos niveles de experiencia digital. |
| Limitado en el tiempo | Sí | La revisión se realiza antes de validar cada conjunto de pantallas principales. |

## RNF-004: Escalabilidad operativa

**Categoría ISO/IEC 25010:** Eficiencia de desempeño / Capacidad  
**Prioridad:** Media-Alta

### Declaración del requisito

El sistema debe soportar el crecimiento operativo hasta **1,000 pedidos diarios y 50 vehículos** sin perder la capacidad de registrar información, consultar datos y ejecutar las funciones esenciales definidas para la operación logística.

### Escenario de Calidad

| Elemento del escenario | Descripción del comportamiento |
|---|---|
| **Fuente** | Crecimiento de la operación de DistriRápido S.A.C. |
| **Estímulo** | Incremento del volumen de pedidos y vehículos gestionados |
| **Entorno** | Operación normal con carga ampliada |
| **Artefacto** | Aplicación, servicios de negocio y almacenamiento de datos |
| **Respuesta** | Mantener disponibles las funciones esenciales del sistema bajo el volumen objetivo |
| **Medida de respuesta** | Soportar hasta 1,000 pedidos diarios y 50 vehículos registrados/gestionados en el escenario de prueba |

### Método de verificación

- Ejecutar una prueba con datos equivalentes a 1,000 pedidos diarios y 50 vehículos.
- Verificar que las operaciones principales puedan completarse sin errores atribuibles al volumen configurado.
- Registrar incidencias de capacidad y comportamiento del sistema.

### Evaluación SMART

| Criterio | Cumplimiento | Justificación |
|---|---|---|
| Específico | Sí | Define explícitamente el volumen objetivo. |
| Medible | Sí | Establece 1,000 pedidos diarios y 50 vehículos. |
| Alcanzable | Sí | Puede probarse con datos sintéticos o de prueba. |
| Relevante | Sí | Responde al crecimiento proyectado de la operación. |
| Limitado en el tiempo | Sí | Se verifica durante las pruebas de capacidad y escalabilidad. |

## RNF-005: Usabilidad para conductores

**Categoría ISO/IEC 25010:** Capacidad de interacción / Usabilidad  
**Prioridad:** Alta

### Declaración del requisito

El sistema debe proporcionar a los conductores una vista simplificada que muestre únicamente la información esencial para ejecutar su recorrido: **ruta asignada, entregas pendientes y alertas de tráfico**.

Durante una prueba de uso, un conductor debe poder identificar estos tres elementos sin requerir acceso a módulos administrativos.

### Escenario de Calidad

| Elemento del escenario | Descripción del comportamiento |
|---|---|
| **Fuente** | Conductor autenticado |
| **Estímulo** | Acceso al modo o vista de conductor |
| **Entorno** | Operación normal durante una jornada de reparto |
| **Artefacto** | Interfaz destinada al conductor |
| **Respuesta** | Mostrar la ruta asignada, las entregas pendientes y las alertas de tráfico, excluyendo funciones administrativas |
| **Medida de respuesta** | 100% de los tres elementos esenciales visibles en la vista evaluada y sin acceso a funciones administrativas no autorizadas |

### Método de verificación

- Ejecutar prueba funcional con un usuario de rol conductor.
- Verificar la presencia de los tres elementos esenciales.
- Comprobar que el usuario no pueda ingresar a módulos administrativos restringidos.

### Evaluación SMART

| Criterio | Cumplimiento | Justificación |
|---|---|---|
| Específico | Sí | Define exactamente qué información debe ver el conductor. |
| Medible | Sí | Se comprueba la presencia de 3 elementos obligatorios y la ausencia de accesos no autorizados. |
| Alcanzable | Sí | Puede verificarse mediante una prueba funcional de interfaz y permisos. |
| Relevante | Sí | Reduce complejidad para el usuario operativo principal en ruta. |
| Limitado en el tiempo | Sí | Se valida durante las pruebas de aceptación de la vista del conductor. |

## RNF-006: Disponibilidad del sistema

**Categoría ISO/IEC 25010:** Fiabilidad / Disponibilidad  
**Prioridad:** Alta

### Declaración del requisito

El sistema debe mantener una disponibilidad mínima de **99.5% durante el horario operativo de 5:00 a. m. a 10:00 p. m.**

El diseño deberá contemplar una alternativa de continuidad operativa ante interrupciones de conectividad o energía que afecten temporalmente el acceso al servicio.

### Escenario de Calidad

| Elemento del escenario | Descripción del comportamiento |
|---|---|
| **Fuente** | Infraestructura, red o suministro eléctrico |
| **Estímulo** | Interrupción parcial o temporal del servicio |
| **Entorno** | Horario operativo de 5:00 a. m. a 10:00 p. m. |
| **Artefacto** | Plataforma EcoLogística Lima |
| **Respuesta** | Mantener el servicio disponible dentro del objetivo establecido y aplicar el mecanismo de contingencia definido cuando corresponda |
| **Medida de respuesta** | Disponibilidad mensual ≥ 99.5% dentro del horario operativo definido |

### Método de verificación

- Registrar periodos de disponibilidad e indisponibilidad dentro del horario operativo.
- Calcular el porcentaje mensual de disponibilidad.
- Probar el mecanismo de contingencia definido por el equipo para escenarios de interrupción.

### Evaluación SMART

| Criterio | Cumplimiento | Justificación |
|---|---|---|
| Específico | Sí | Define horario y comportamiento de disponibilidad. |
| Medible | Sí | Establece un objetivo de 99.5%. |
| Alcanzable | Sí | Puede medirse mediante registros de disponibilidad durante las pruebas o despliegue. |
| Relevante | Sí | El sistema apoya una operación logística diaria. |
| Limitado en el tiempo | Sí | La disponibilidad se calcula mensualmente dentro del horario establecido. |

## RNF-007: Documentación técnica y operativa

**Categoría ISO/IEC 25010:** Mantenibilidad / Capacidad de interacción  
**Prioridad:** Media

### Declaración del requisito

El proyecto debe contar con documentación actualizada que cubra, como mínimo:

1. Proceso de desarrollo.
2. Arquitectura del sistema.
3. Manual de usuario.
4. Manual de administrador.
5. Documentación de la API.
6. Contexto logístico de Lima relacionado con vías, horas punta y normativa de tránsito considerada en el proyecto.

La documentación deberá corresponder a la versión del sistema entregada en cada hito académico o versión liberada.

### Escenario de Calidad

| Elemento del escenario | Descripción del comportamiento |
|---|---|
| **Fuente** | Equipo de desarrollo, docente, administrador o usuario autorizado |
| **Estímulo** | Necesidad de consultar información técnica u operativa del sistema |
| **Entorno** | Revisión de una versión entregable del proyecto |
| **Artefacto** | Repositorio de documentación del proyecto |
| **Respuesta** | Proporcionar documentos actualizados y coherentes con la versión evaluada |
| **Medida de respuesta** | 100% de los 6 grupos documentales mínimos presentes y revisados en el hito correspondiente |

### Método de verificación

- Aplicar una lista de comprobación documental.
- Verificar existencia, versión y correspondencia con la funcionalidad entregada.
- Registrar documentos faltantes o desactualizados antes del cierre del hito.

### Evaluación SMART

| Criterio | Cumplimiento | Justificación |
|---|---|---|
| Específico | Sí | Define los grupos de documentación requeridos. |
| Medible | Sí | Se verifica la presencia del 100% de los 6 grupos mínimos. |
| Alcanzable | Sí | Puede controlarse mediante una lista de comprobación. |
| Relevante | Sí | Facilita operación, mantenimiento, evaluación y transferencia de conocimiento. |
| Limitado en el tiempo | Sí | La revisión se realiza en cada hito académico o versión liberada. |

# 7. Criterios generales de aceptación

El conjunto de requisitos no funcionales se considerará aceptado cuando:

- Cada requisito cuente con una métrica verificable.
- Cada escenario especifique fuente, estímulo, entorno, artefacto, respuesta y medida de respuesta.
- Los métodos de prueba permitan obtener evidencia objetiva de cumplimiento.
- Las métricas se encuentren alineadas con el contexto operativo de EcoLogística Lima.
- No se utilicen expresiones ambiguas sin una condición de verificación.
- Los resultados de las pruebas queden registrados como evidencia del proyecto.
