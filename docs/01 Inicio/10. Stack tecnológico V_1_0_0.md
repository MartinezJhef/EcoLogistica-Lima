## 3. Stack Tecnológico Seleccionado y Componentes de Arquitectura

### 3.1. Decisión de Selección
La **Alternativa 2 — Python + FastAPI + React + PostgreSQL** obtuvo el puntaje más alto de la evaluación multidimensional, con **9.1/10 (Alto)**. La selección se fundamenta en su mayor alineación con los requerimientos funcionales y técnicos del proyecto **EcoLogistica-Lima (PFA-ECOLIMA-2026)**, especialmente en el procesamiento de algoritmos de optimización, gestión de información relacional y geoespacial, desarrollo de APIs y experiencia técnica disponible en el equipo.

La combinación seleccionada permite mantener una arquitectura tecnológica integrada, evitando incorporar servicios independientes para los componentes de optimización y procesamiento de datos. Asimismo, PostgreSQL con PostGIS permite gestionar información relacional y geoespacial dentro de una misma plataforma de datos.

La decisión también considera la necesidad de implementar la solución en infraestructura cloud con capacidad de crecimiento progresivo dentro del plazo de 16 semanas, manteniendo un uso responsable de los recursos computacionales y evitando asignar recursos superiores a los requeridos por la carga real del sistema.

## 4. Justificación Técnica Formal

### 4.1 Frontend — React

React fue seleccionado para la capa de presentación debido a su arquitectura basada en componentes y su amplio ecosistema para el desarrollo de aplicaciones web.

Las principales razones son:

- **Arquitectura basada en componentes:** permite dividir la interfaz en componentes reutilizables, facilitando el mantenimiento y evolución del sistema.
- **Reutilización de código:** componentes como formularios, tablas, mapas, indicadores y paneles pueden reutilizarse en diferentes módulos de la aplicación.
- **Integración con servicios REST:** React puede consumir las APIs desarrolladas con FastAPI mediante solicitudes HTTP, permitiendo separar claramente la interfaz de usuario de la lógica de negocio.
- **Ecosistema:** dispone de un amplio conjunto de librerías para interfaces, visualización de datos, mapas y gestión del estado de las aplicaciones.
- **Escalabilidad funcional:** la arquitectura por componentes facilita incorporar nuevos módulos sin tener que reconstruir completamente la interfaz.
- **Adecuación al perfil del equipo:** el uso de JavaScript en el frontend permite aprovechar los conocimientos existentes del equipo y reducir la curva de aprendizaje de la solución.

Por estas razones, React constituye una alternativa adecuada para construir una interfaz modular y mantenible para el sistema.

---

### 4.2 Backend — Python + FastAPI

Python + FastAPI fue seleccionado para la capa backend debido a la necesidad de integrar servicios web con algoritmos de optimización y procesamiento de datos.

Las principales razones son:

- **Integración con algoritmos de optimización:** Python dispone de un amplio ecosistema para computación científica, inteligencia artificial y optimización, permitiendo implementar los algoritmos requeridos directamente dentro del backend.
- **Integración entre capas:** al utilizar Python para el desarrollo de los algoritmos y del backend, se evita la necesidad de implementar un servicio adicional exclusivamente para ejecutar los algoritmos de optimización.
- **Rendimiento:** FastAPI está basado en ASGI y proporciona soporte para operaciones asíncronas, siendo apropiado para la construcción de APIs de alto rendimiento.
- **Documentación automática:** FastAPI genera automáticamente documentación de la API mediante OpenAPI, incluyendo interfaces como Swagger UI y ReDoc.
- **Validación de datos:** FastAPI utiliza Pydantic para definir y validar los datos recibidos por los endpoints, contribuyendo a reducir errores en el procesamiento de las solicitudes.
- **Arquitectura modular:** permite separar los endpoints, servicios, modelos, esquemas y lógica de negocio, facilitando el mantenimiento y crecimiento de la aplicación.
- **Perfil del equipo:** Python presenta una mayor afinidad con las actividades de inteligencia artificial, optimización y procesamiento de datos consideradas en el proyecto.
- **Eficiencia en la nube:** FastAPI permite desarrollar servicios asíncronos y ligeros para determinadas cargas de trabajo. Esto facilita dimensionar los recursos cloud de acuerdo con la demanda real, contribuyendo al uso eficiente de CPU y memoria.

Por estas características, FastAPI permite centralizar en un mismo backend la lógica de negocio, los servicios API y los componentes de optimización.

---

### 4.3 Base de Datos — PostgreSQL + PostGIS

PostgreSQL fue seleccionado como sistema gestor de base de datos debido a la naturaleza relacional de la información administrada por el sistema y a la necesidad de incorporar información geoespacial.

Las principales razones son:

- **Modelo relacional:** permite representar entidades y relaciones mediante tablas, claves primarias y claves foráneas, facilitando la integridad y consistencia de la información.
- **Integridad de datos:** PostgreSQL proporciona características de transacciones y cumplimiento de propiedades ACID, adecuadas para información que requiere consistencia.
- **Soporte geoespacial:** mediante la extensión PostGIS es posible almacenar, consultar y procesar coordenadas y otros tipos de información geográfica.
- **Información de ubicación:** PostGIS permite gestionar datos georreferenciados relacionados con las rutas, ubicaciones y elementos geográficos utilizados por el sistema en **Lima**.
- **Consultas espaciales:** permite realizar operaciones geográficas mediante índices y funciones espaciales, reduciendo la necesidad de trasladar todo el procesamiento geográfico a la aplicación.
- **Escalabilidad:** PostgreSQL permite incrementar progresivamente los recursos de infraestructura y utilizar mecanismos de optimización, indexación y replicación cuando el crecimiento de la solución lo requiera.
- **Código abierto:** PostgreSQL es software libre y de código abierto, evitando costos de licenciamiento asociados al motor de base de datos.
- **Integración con FastAPI:** Python dispone de diferentes herramientas y controladores para trabajar con PostgreSQL, permitiendo integrar la base de datos directamente con los servicios backend.

La utilización conjunta de PostgreSQL y PostGIS permite mantener en una única plataforma la información transaccional y geoespacial requerida por el sistema.

---

### 4.4 Comunicación entre Frontend y Backend — API REST

La comunicación entre React y FastAPI se realizará mediante una API REST.

Esta decisión permite:

- **Separación de responsabilidades:** React se encarga de la presentación, mientras FastAPI concentra la lógica de negocio y acceso a datos.
- **Interoperabilidad:** la API puede ser consumida por diferentes clientes que utilicen HTTP y formatos como JSON.
- **Mantenibilidad:** la separación entre frontend y backend permite modificar una capa sin tener que reconstruir completamente la otra.
- **Escalabilidad independiente:** frontend y backend pueden desplegarse y dimensionarse de manera independiente en infraestructura cloud.
- **Documentación:** FastAPI permite documentar automáticamente los endpoints mediante OpenAPI.
- **Seguridad:** la API puede incorporar mecanismos de autenticación, autorización, validación de entradas y control de acceso.

Esta separación contribuye a una arquitectura modular que puede evolucionar conforme aumenten los usuarios y funcionalidades del sistema.

---

### 4.5 Arquitectura Cloud y Escalabilidad

La solución se diseñará considerando un despliegue progresivo en infraestructura cloud. La selección de React, FastAPI y PostgreSQL permite separar las principales capas de la solución y escalar los componentes de acuerdo con sus necesidades.

La arquitectura considera:

- **Frontend independiente:** React puede desplegarse como una aplicación web independiente.
- **Backend desacoplado:** FastAPI funcionará como una capa de servicios que puede escalar horizontalmente cuando aumente la cantidad de solicitudes.
- **Base de datos centralizada:** PostgreSQL administrará la información transaccional y geoespacial.
- **Escalabilidad horizontal:** cuando la demanda del backend aumente, pueden incorporarse instancias adicionales del servicio API detrás de un balanceador de carga.
- **Escalabilidad vertical:** inicialmente pueden incrementarse CPU, memoria o almacenamiento de los recursos cloud cuando la carga lo requiera.
- **Optimización de recursos:** el dimensionamiento se realizará de acuerdo con la demanda real, evitando asignar recursos excesivos durante las primeras etapas.
- **Separación de servicios:** la separación entre frontend, backend y base de datos facilita realizar modificaciones y ampliaciones sin afectar toda la solución.
- **Evolución progresiva:** la arquitectura permite incorporar posteriormente mecanismos como caché, balanceo de carga, réplicas de lectura y procesamiento asíncrono si el crecimiento del sistema lo requiere.

De esta manera, la arquitectura no depende de disponer desde el inicio de una infraestructura sobredimensionada, sino que permite aumentar los recursos conforme evolucione la demanda.

### 4.6 Criterio de Bajo Consumo Energético y Green Software

El criterio de bajo consumo energético se incorpora mediante el **uso eficiente de los recursos computacionales**, evitando considerar que una tecnología es automáticamente "verde" únicamente por utilizar determinado lenguaje o framework.

La propuesta contempla:

- **Dimensionamiento adecuado:** asignar CPU, memoria y almacenamiento de acuerdo con la demanda real del sistema.
- **Servicios eficientes:** utilizar FastAPI y operaciones asíncronas cuando sean apropiadas para el tipo de carga.
- **Optimización de consultas:** utilizar índices y consultas eficientes en PostgreSQL/PostGIS para reducir operaciones innecesarias.
- **Procesamiento geoespacial en la base de datos:** aprovechar PostGIS para ejecutar operaciones espaciales mediante el motor de base de datos en lugar de transferir grandes cantidades de información innecesariamente a la aplicación.
- **Escalamiento bajo demanda:** incrementar recursos solamente cuando la carga del sistema lo requiera.
- **Reducción de procesamiento innecesario:** evitar tareas, consultas y procesos que no aporten valor funcional.
- **Uso de infraestructura cloud:** aprovechar mecanismos de escalamiento y dimensionamiento disponibles en la infraestructura cloud para evitar mantener permanentemente recursos sobredimensionados.
- **Monitoreo:** supervisar consumo de CPU, memoria, almacenamiento y tráfico para identificar oportunidades de optimización.

Por tanto, el criterio de eficiencia energética se aborda desde la arquitectura completa y la gestión de recursos, y no únicamente desde la elección del lenguaje de programación.

### 4.7 Alineación con el Perfil del Equipo

La selección tecnológica también considera las capacidades actuales del equipo.

Python resulta especialmente conveniente debido a su utilización en:

- desarrollo de algoritmos;
- inteligencia artificial;
- procesamiento de datos;
- optimización;
- experimentación y validación de modelos.

Por otro lado, React permite aprovechar conocimientos de JavaScript para el desarrollo de la interfaz web.

Esta combinación reduce la necesidad de incorporar un tercer lenguaje principal para implementar los algoritmos de optimización, permitiendo que el equipo concentre el desarrollo del backend y los algoritmos en Python.

En comparación, la alternativa Java Spring Boot + Angular requeriría incorporar Java, Spring Boot y Angular como tecnologías principales, incrementando la curva de aprendizaje para el equipo.
